### 3) Позитивные наблюдения

- **Append-only инвариант образцовый.** `CharacterAbility.java:12-15,16-54` документирует `append, never renumber`, enum 10 слотов 0-9 contiguous, `CharacterAbilityWireFormatTest.java:29-91` пинит `SHIPPED_IDS` 0-9, `ordinal==networkId` (58-59), `values().length` growth detection (45), `byNetworkId==null` для unknown (76-79), `idsAreUniqueAndNonNegative` (83-91) — одна из самых сильных гарантий в репо. Переименование/перенумерация не скомпилируется/не пройдёт тест.
- **Vessel claim verification — корректная server-authoritative схема.** `CharacterAbilityPayload` несёт `characterId` именно как claim (javadoc 16-18), `JujutsuNetworking:50-55` сравнивает с `CharacterSelectionManager.selected(player)` (тот же источник, что и `CharacterAbilityCooldowns.keyFor:66`). Комментарий 50-53 точно описывает race окна меню (optimistic `applyLocal` + close before server echo). `CharacterAbilityCooldowns` и `JujutsuNetworking.sendAbilityCooldown:94` резолвят vessel из одного authoritative источника — рассинхрон ` (player,slot)` vs `(player,vessel,slot)` из javadoc `CharacterAbilityCooldowns:11-16` исправлен.
- **Отсутствие vessel-specific payload подтверждено bytecode-правилом.** `VesselBoundaryTest.thePacketSurfaceIsExactlyWhatWeThinkItIs:281-297` считает инвентарь `CustomPacketPayload` из обоих outputs (main+client), `noVesselOwnsItsOwnAbilityPacket:299-315` банит payload'ы в vessel-пакетах (`allowEmptyShould` для client output где payload'ов нет). E13 закрыт — `JujutsuNetworking` больше не называет `SelfResonanceRuntime` через inline FQN.
- **Ключ cooldown'ов правильно включает vessel.** `CharacterAbilityCooldowns:65-67 Key(UUID, JujutsuCharacter, CharacterAbility)` — по `AGENTS.md:36` слот=позиция ввода, разный vessel=разная способность. `ClientAbilityCooldowns:56 Key(JujutsuCharacter, CharacterAbility)` — без `playerId`, что корректно для single-player клиента (playerId не нужен, один локальный игрок). `AbilityCooldownPayload:9` везёт `characterId` для зеркала. E1a документирует `copyOnDeath` для `CHARACTER_STATE` и политику survive-respawn.
- **Forward-compat для unknown slot.** `CharacterAbility.byNetworkId:66-73` возвращает `null`, `handleCharacterAbility:46-48` silent return, `ClientAbilityCooldowns.apply:18,20-22` `if (ability==null) return` — новый клиент со слотом 10 не крашит старый сервер, новая S2C cooldown-синхронизация c unknown id не отравляет client map. `CharacterAbilityWireFormatTest:72-79` это пинит.
- **Wire caps консистентны.** Все `characterId` — `writeUtf(*,32)` / `readUtf(32)` (`CharacterAbilityPayload:28,33`, `AbilityCooldownPayload:17,21`, `SelectCharacterPayload:16,20`, `CharacterSelectionSyncPayload:17,22`). `modelId` — `16` (`CharacterSelectionSyncPayload:17,23`), протестировано `SelectionPayloadCodecTest:54-65` на различие caps. Нет расхождений write/read; `buffer.readUtf(32)` отклонит >32 как `DecoderException`.
- **Server-authoritative executor без vessel-ветвлений.** `CharacterAbilityExecutor:15-35` — единственные shared checks `NONE` (17-22) и `isReady` (27-33) до делегирования в `definition.tryCast`. Нет per-vessel `if` в shared коде (проверено `VesselBoundaryTest.sharedServerCodeAsksTheVesselRatherThanNamingOne:232-244`).
- **Thread-affinity корректна.** Все C2S handlers обёрнуты в `context.server().execute` (`JujutsuNetworking:32-40`), `CharacterAbilityCooldowns.READY_AT` HashMap доступен только с server thread — безопасно (хотя несогласован с `CombatStagger` ConcurrentHashMap, но оба корректны).
