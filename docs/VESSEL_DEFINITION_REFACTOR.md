# Рефакторинг: слоты ввода и определения персонажей

Ветка `feat/todo-input-slots`, шесть коммитов от `d80a9c9` до `53a4dcd`, база `main` = `00e6846`.

Документ описывает, что было сделано, почему, как было устроено раньше и что это даёт. Технически и подробно. Формулировки контрактов — в [Vessel definitions](../Jujutsu%20Kaizen/jujutsumod-codebase-codex/02-architecture/Vessel-definitions.md); здесь — история и обоснование.

---

## 1. Проблема, с которой всё началось

Персонажей было двое, и добавление третьего требовало правок в **девяти** общих файлах. Ни один из них не был «про персонажа» — каждый просто содержал ветку с его именем:

| Файл | Что в нём ветвилось |
|---|---|
| `JujutsuKeybinds` | какую способность отправить по клавише — по персонажу |
| `CharacterAbilityExecutor` | `switch` по персонажу на рантайм |
| `CharacterCombatModifiers` | `if (selected != TODO) return` для атрибутов и стаггера |
| `CharacterSelectionManager` | `if (character == NOBARA)` для стартового набора |
| `JujutsuMod` | двенадцать вызовов `register()` рантаймов персонажей |
| `CharacterGeoRenderers` | `switch` на рендерер |
| `ClickGuiTheme` | два `switch` на цвет плюс тернарная цепочка |
| `CharacterRosterPanel` | массив карточек с данными всех персонажей |
| `JujutsuModules` | три вручную собранные строки вкладки |
| `JujutsuVfxRecipes` | два вызова регистрации VFX |
| `CharacterSkinMixin` | `switch` на текстуру скина |

Плюс два разных пути ввода: у Тодо — общий `CharacterAbilityPayload`, у Нобары — собственный `NobaraActionPayload` с int-идентификаторами действий и отдельный гейт `ProjectJjkNobaraActions`. Именно это расхождение и было корнем: два пути не могли договориться, что значит нажатие клавиши.

## 2. Шаг 1 — слоты назвали по позиции ввода (`d80a9c9`)

### Как было

`CharacterAbility` назывался по смыслу способности: `PRIMARY`, `SECONDARY`, `TERTIARY`. У Тодо `SECONDARY` означал фейк (Shift+R), `TERTIARY` — парный своп (B). У Нобары своих констант вообще не было — она ездила на int'ах.

Проблема: имя `SECONDARY` не говорило, **какой ввод** до него доходит. Файл клавиш вынужден был знать, что для Тодо Shift+R это `SECONDARY`, а для Нобары — `SELF_RESONANCE`. То есть знание о персонаже жило в слое ввода.

### Как стало

```java
PRIMARY(0),         // R
PRIMARY_SNEAK(1),   // Shift+R
SECONDARY(2),       // B
SECONDARY_SNEAK(3), // Shift+B
ATTACK_CONTEXT(4);  // ЛКМ с оружием техники
```

Слот теперь называет **позицию ввода**, а не смысл. Что делает мой `PRIMARY_SNEAK` — вопрос к персонажу, а не к клавише.

### Почему перенумерация была безопасна

Эти id ездят только в `CharacterAbilityPayload` (C2S) и `AbilityCooldownPayload` (S2C) и живут в памяти. В сохранение пишется id **персонажа**, а не слота. Проверено грепом по всем местам сериализации.

## 3. Шаг 2 — слой ввода стал переводчиком (`8a2c078`)

### Как было

```java
while (nobaraEnlarge.consumeClick()) {
    JujutsuCharacter character = selectedCharacter(client);
    if (character == JujutsuCharacter.TODO) {
        sendCharacterAbility(character, client.player.isShiftKeyDown()
                ? CharacterAbility.PRIMARY_SNEAK : CharacterAbility.PRIMARY);
    } else if (character == JujutsuCharacter.NOBARA) {
        sendNobaraAction(client.player.isShiftKeyDown()
                ? NobaraActionPayload.SELF_RESONANCE : NobaraActionPayload.HAIRPIN_DIRECTED);
    }
}
```

### Как стало

```java
while (techniqueKey.consumeClick()) {
    sendCharacterAbility(client, slot(client, CharacterAbility.PRIMARY, CharacterAbility.PRIMARY_SNEAK));
}
```

Весь контракт ввода — в одном выражении:

```java
private static CharacterAbility slot(Minecraft client, CharacterAbility tap, CharacterAbility sneak) {
    return client.player != null && client.player.isShiftKeyDown() ? sneak : tap;
}
```

### Что чем помогает

Файл клавиш перестал знать о персонажах. Единственный вопрос, который он задаёт, — «я вообще персонаж?», чтобы случайное нажатие без выбранного персонажа не выдавало сообщение.

### Побочное следствие, названное вслух

Раньше `Shift+B` доходил до парного свопа Тодо, потому что клавиша **игнорировала приседание**. Теперь это `SECONDARY_SNEAK`, на который его роутер отвечает явным `false` — тихий no-op. Это оказалось хуже, чем выглядело: парный своп двухнажатийный, и присесть между нажатиями — обычное дело при прицеливании. Записано, откат — одна строка.

### Что осталось намеренно

Строковые id биндов остались `key.jujutsumod.nobara_hairpin_*`, потому что ванилла пишет именно эту строку в `options.txt` — переименование молча сбросило бы всем настройку клавиш. Отображаемые названия уже были нейтральными.

## 4. Шаг 3 — миграция Нобары (`9cdfaac`)

Единственный шаг, который мог сломать работающее.

### Что удалено

- `network/NobaraActionPayload.java` — пакет с int-идентификатором действия
- `character/nobara/projectjjk/ProjectJjkNobaraActions.java` — int-гейт
- регистрация пакета и обработчик в `JujutsuNetworking`
- метод `sendNobaraAction` в `JujutsuKeybinds`
- осиротевший ключ локализации `nobara.action.not_selected` в обеих локализациях

### Что появилось

`character/nobara/NobaraAbilityRouter.java` — исчерпывающий `switch` без `default`:

```java
case PRIMARY         -> canCastMarkedHairpin && startDirectedHairpin
case PRIMARY_SNEAK   -> SelfResonanceRuntime.tryCast
case SECONDARY       -> canCastMarkedHairpin && startMassHairpin
case SECONDARY_SNEAK -> NailTrapRuntime.tryPlace
case ATTACK_CONTEXT  -> NobaraHammerCombatRuntime.handleInput
```

Роутер забрал две вещи, которые есть у неё и нет у Тодо, и которым не место в общем исполнителе: **проверку стаггера** (до switch, молча, ровно как в удалённом гейте) и **единственную строку-отказ** на провал каста.

### Две регрессии, вскрытые миграцией и починенные там же

**Кулдаун переезжал между персонажами.** Серверный ключ был `(UUID, слот)`, клиентское зеркало — `(персонаж, слот)`. Пока Нобара обходила общий исполнитель, расхождение не проявлялось. После миграции кулдаун парного свопа Тодо (100 тиков) отказывал массовой Шпильке Нобары на том же слоте, причём клиент рисовал способность готовой, потому что его ключ включал персонажа. Серверный ключ получил персонажа, а `sendAbilityCooldown` потерял параметр персонажа и выводит его из того же источника — чтобы две стороны не могли разойтись.

**Команда `/jujutsu hairpin enlarge` кастовала не то.** Она нацелена на слот, а `PRIMARY` за Тодо — телепорт. Команда с именем «Hairpin» выстрелила бы свопом и отчиталась «Cast Hairpin Enlarge». Добавлена явная проверка, что вызывающий — Нобара.

## 5. Шаг 3.5 — устаревший персонаж в запросе (`d9df2b5`)

Найдено адверсарным ревью, а не мной.

### Механика бага

`CharacterRosterPanel.applySelection` применяет персонажа **локально** и сразу закрывает меню, а сервер узнаёт из `SelectCharacterPayload`. В окно между этим клиент считает себя Нобарой, сервер — ещё Тодо. Нажатие `R` внутри окна отправляет `PRIMARY`, сервер диспетчеризует по **своему** состоянию и запускает настоящий телепорт Тодо с его шестидесятитиковым кулдауном.

Раньше это чинилось само: у Нобары был свой пакет, и её гейт отвечал «выбери Нобару». Удалив второй путь, я удалил и это свойство — в обе стороны.

### Решение

`CharacterAbilityPayload` теперь `(int abilityId, String characterId)`. Клиент штампует персонажа, которого показывал игроку; сервер сравнивает со своим и молча отказывает при расхождении. Поле только сравнивается — сервер по-прежнему решает сам.

### Дефекты в моих же тестах, найденные тем же ревью

- **Карта слотов не проверялась.** Тест искал каждый вызов *где угодно в файле*, поэтому перестановка `PRIMARY` и `SECONDARY` — то есть `R` кастует массовую Шпильку, а `B` направленную — оставалась зелёной. Переписано на разбор текста конкретной ветки `case`, подтверждено мутацией.
- **Тест кулдауна** проверял только текст двух объявлений `record`. Константа вместо живого чтения прошла бы. Теперь пинится источник значения на обеих сторонах.
- **`!contains("default ->")`** обходился одним лишним пробелом. Заменено на регулярное выражение.

## 6. Шаг 4 — серверные определения (`29dd4c4`, `8561cf7`)

### Интерфейс

`CharacterDefinition`: обязательны `id()` и `tryCast()`. Остальное — безопасные `default`:

| Хук | По умолчанию | Кто переопределяет |
|---|---|---|
| `registerServerHooks()` | ничего | оба (8 рантаймов у Нобары, 4 у Тодо) |
| `applyAttributes` / `removeAttributes` | ничего | только Тодо |
| `adjustIncomingStaggerTicks(int)` | без изменений | только Тодо |
| `onSelected` | ничего | только Нобара (стартовый набор) |
| `onDeselected` | ничего | только Тодо (метки и незавершённый своп) |

Определение Нобары — двадцать строк, и в них нет ни одного метода, который к ней не относится.

### Реестр

`JujutsuCharacters.definition(JujutsuCharacter)` — исчерпывающий `switch` без `default`. Это **единственная** compile-time гарантия на сервере: новая константа `JujutsuCharacter` останавливает компиляцию здесь, пока не будет привязана.

`all()` выводится из `JujutsuCharacter.values()`, а не пишется рядом со switch. Второй список, поддерживаемый руками, — единственное, что может разойтись со switch, не сломав компиляцию.

### Что перестало ветвиться

```java
// было
return switch (character) {
    case NOBARA -> NobaraAbilityRouter.tryCast(player, ability, notify);
    case TODO -> TodoAbilityRouter.tryCast(player, ability, notify);
    case NONE -> false;
};

// стало
return JujutsuCharacters.definition(character).tryCast(player, ability, notify);
```

```java
// было: общий файл знает id атрибутов Тодо
clearTodoModifiers(player);
if (selected != JujutsuCharacter.TODO) return;
addMultiplier(..., TODO_DAMAGE_ID, TodoProfile.MELEE_DAMAGE_MULTIPLIER - 1.0);

// стало: каждый снимает своё, выбранный добавляет своё
for (CharacterDefinition definition : JujutsuCharacters.all()) definition.removeAttributes(player);
JujutsuCharacters.definition(selected).applyAttributes(player);
```

### Правки по адверсарному ревью (`8561cf7`)

**Мой javadoc врал.** Интерфейс утверждал «добавление персонажа не трогает ни одного общего файла», а `JujutsuMod` вручную перечислял двенадцать регистраций. Появился `registerServerHooks()`, mod init крутит цикл по реестру. Проверил, что ничего не потерялось: тест **выводит ожидаемый список из дерева исходников** — любой класс в пакете персонажа с `public static void register()`, который никто не зовёт, роняет сборку. Подтверждено мутацией: незарегистрированный слушатель не даёт ошибки нигде и просто молча не работает.

**`adjustStaggerTicks` возвращал 1 на запрос 0** — выдумывал стаггер из ничего. Работало только потому, что единственный вызывающий отсекает ноль раньше, а инвариант жил в другом файле. Теперь метод защищает себя сам, инвариант записан в контракте, и метод назван по направлению (`adjustIncomingStaggerTicks`), потому что в проекте два стаггер-правила и они различались одним словом.

**`grantsStarterKit()` удалён.** Он писал в сохранение флаг, который никто не читает, и делал не то, что называется: набор выдаёт `onSelected`, а связи между хуком и выдачей не было. Заявка теперь записывается для любого персонажа — это факт об игроке, а не вопрос к персонажу.

**Поля реестра переименованы в `*_DEFINITION`**, потому что при коротких именах `case NOBARA -> TODO` выглядит ровно как правильная строка.

### Два отступления от плана

План клал ключи локализации в серверное определение. Ключи оказались не набором: три слота карточки означают у разных персонажей разное, полное имя Нобары лежит под ключом, который не выводится ни из какого правила, а для `NONE` ключа под его id нет вообще. Производный `nameKey()` был неверен для двух персонажей из трёх и не имел ни одного вызова — строки отображения ушли в клиентское определение.

Перенос очистки Тодо в его `onDeselected` означает, что она срабатывает при уходе от него, а не на любой смене персонажа. Это перестало уничтожать метку, брошенную тем, кто Тодо никогда не был, — что возможно, потому что у предмета-метки нет проверки персонажа. Записано как E12.

## 7. Шаг 5 — клиентские определения (`53a4dcd`)

### Почему это отдельный интерфейс, а не расширение серверного

Выделенный сервер загружает `CharacterDefinition` и **каждую его реализацию**. Рендерер, тема или VFX-рецепт, достижимые оттуда, притащили бы клиентские классы на машину, где их нет, и падение случилось бы при загрузке класса — далеко от строки, которая его вызвала. Две половины связаны только константой `JujutsuCharacter`.

Тест обходит **весь** `src/main` и роняет сборку на любом упоминании `net.minecraft.client` или `jujutsu.mod.client`.

### Что перестало ветвиться

Пять общих клиентских файлов: тема, карта рендереров, вкладка модулей, ростер, init. Плюс миксин скина. `JujutsuVfxRecipes` удалён целиком — каждый персонаж регистрирует свой пакет, поэтому список «у кого есть рецепты» не может разойтись со списком «кто существует».

### Данные ростера были неверны, и перенос это вскрыл

Запись имела поля `name/technique/grade`. Нобара передавала в них полное имя, роль и ранг; Тодо — имя, технику и роль. То есть имена полей были неверны для одного из них при любом прочтении. Стали `nameKey/roleKey/subtitleKey`.

Заметнее другое — полоски способностей врали:

| | Было | Стало |
|---|---|---|
| Нобара | 4 записи на 5 занятых слотов; ЛКМ подписан «Boom»; ловушка не упомянута; показано «Пробитие», которого нет ни на одном слоте | 5 записей ровно по тому, что отвечает её роутер |
| Тодо | 1 запись на 3 занятых слота | 3 записи |

То есть про фейк и парный своп игрок мог узнать только из changelog, а не из меню. Три нужных ключа локализации уже существовали и не использовались; два добавлены в обе локализации.

### Порядок карточек

Порядок enum — `NONE, NOBARA, TODO`, а в меню Нобара всегда была первой, а «Нет» последним. Вывод карточек из реестра молча переставил бы их. Порядок стал собственным ответом определения (`rosterOrder()`).

### Пути скинов

Были объявлены дважды — в миксине скина и в ростере. Теперь путь принадлежит персонажу, оба читают оттуда.

## 8. Итог: что даёт

### Точки правки при добавлении персонажа

| | Было | Стало |
|---|---|---|
| Общие файлы, которые надо править | 9–11 | **0** |
| Файлы персонажа | 2 рантайма | 1 серверное + 1 клиентское определение |
| Места регистрации | разбросаны по mod init, VFX-агрегатору, ростеру, теме | 2 строки в двух реестрах |
| Что ловит забытое | ничего | компиляция в обоих реестрах |

Выигрыш не в «одной строке» — его и не обещается. Выигрыш в том, что **общие файлы перестали меняться вообще**, и ни одна точка правки не содержит логики персонажа.

### Гарантии, и чем они различаются

Различение важное, его легко смазать:

- **Compile-time** — исчерпывающий `switch` без `default`, ровно в двух местах. Новая константа `JujutsuCharacter` останавливает **компиляцию**, пока не привязана на обеих сторонах.
- **Build-time** — реестровые тесты. Они ловят то, чего switch выразить не может: что определение признаёт ту константу, к которой привязано (`case TODO -> NOBARA_DEFINITION` компилируется), что в общий исходный набор не попал клиентский тип, что каждый рантайм персонажа с `register()` действительно вызывается, и что обход для очистки атрибутов покрывает каждого ровно один раз.

`switch` — несущая конструкция, тест — страховка. Наоборот не работает.

### Проверки

JavaExec-программы верификации подтверждаются `./gradlew verifyAssertionsEnabled`; три из них — `NobaraAbilitySlotsTest`, `CharacterDefinitionRegistryTest`, `CharacterClientRegistryTest`. Два ключевых теста подтверждены **мутацией**, а не только зелёным прогоном:

- перестановка веток роутера → падение с «PRIMARY must reach startDirectedHairpin»
- `case TODO -> NOBARA` в реестре → падение с «The registry bound TODO to a definition that claims to be NOBARA»

Doc-аудит проходит. Полная сборка зелёная.

### Записанные, но не починенные дефекты

Все три меняют то, что видит игрок, поэтому протаскивать их внутри рефакторинга было бы неправильно:

- **E10** — общая строка-отказ Нобары затирает пять конкретных переведённых сообщений. Досталось дословно от удалённого гейта. Важное уточнение: расширение возвращаемого типа `tryCast` этого **не** чинит — роутер не может отличить «рантайм уже объяснился» от «ничего не найдено», это знают только сами рантаймы.
- **E11** — сообщение о кулдауне идёт до молчаливой проверки стаггера. Сейчас недостижимо: ни одна её способность не берёт кулдаун.
- **E12** — у предмета-метки нет проверки персонажа, поэтому её может бросить кто угодно. Чинится в слое, который теперь появился.

### Что осталось по персонажам намеренно

- `JujutsuCommands` гейтит команды `hairpin` на Нобару — иначе команда с её именем выстрелила бы способностью другого персонажа на том же слоте.
- `TodoBlackFlashRuntime` проверяет, что бьющий — Тодо. Это слушатель персонажа, фильтрующий сам себя, а не общий код, ветвящийся по персонажу.
- `JujutsuKeybinds` всё ещё перечисляет два молота Нобары, решая, считать ли ЛКМ за `ATTACK_CONTEXT`. Последняя персонажная строка в слое ввода.
