## Сводка

Большой задел под проклятые инциденты (#110): новый пакет `cursedincident` с чистым разрезом «логика ↔ мир» (`IncidentControl` / `IncidentWorldSink`), персистентность через `SavedData`, командная поверхность `/jujutsu incident`, 15 MCP-инструментов, GameTest-оркулы и клиентская атмосфера. ~10k строк, читаемо, политики вынесены в чистые `policy/*`.

Риск: **High** — не из-за архитектуры (каркас в целом верный), а из-за hot-path и state-sync дефектов: `PressureRuntime` исполняет весь спавн-блок каждый тик вместо раза в 2 минуты; синк печати «запись ↔ компонент» односторонний и затирает авторитетное состояние; запечатанный инцидент продолжает эскалацию; все каденсы/очередь правок/объявленные узлы транзиентны — рестарт даёт шторм работы и молчаливую потерю отложенных правок.

## Сильные стороны

- Разрез `IncidentControl` (логика) ↔ `IncidentWorldSink`/`InfectionSink` (мир): тестируемо без мира, команды и MCP идут через тот же API — ровно то, что требует AGENTS.md.
- Персистентность продумана: codec с безопасными дефолтами, drop corrupt-записей с логом, индекс `INCIDENT_BY_OBJECT` с heal-scan fallback.
- Детерминизм сидом (`seed ^ stage.ordinal() ^ …`), чистые политики, удобные `SpawnRequest`-override'ы для тестов.
- VFX переиспользует общий `VfxCue`/`VfxDirector`; клиентская часть изолирована в `src/client`; `IncidentPerceptionBridge` с серверным дефолтом и клиентской установкой — seam сохранён, vessel-нарушений нет (подсистема vessel-нейтральна, что правильно для мировой механики).
- Команды и MCP-инструменты валидируют аргументы (finite-проверки, парсинг stage/knowledge); `drainLoaded` корректно откладывает правки из `CHUNK_LOAD` во избежание рекурсивного setBlock.
- Тесты с диагностикой фикстур; `KNOWN_ISSUES` честно фиксирует принятые ограничения (тип `null` у ролльнутых спавнов, race в drain-тестах).

## Проблемы

1. **[blocker]** `PressureRuntime.tick` — якорь `lastTickGameTime` не двигается между дневными границами → после первых ~2 минут весь блок (включая `IncidentControl.list()` с материализацией InspectView и спавн-ролл) исполняется **каждый тик**; кривая давления фактически бинарна (инлайн №1).
2. **[major]** `applyTransition`: `applyStageDelta` видит старую стадию — переходная волна спавна идёт по таблице предыдущей стадии (инлайн №2).
3. **[major]** Вторичные узлы создаются в центре родителя и не получают никакой работы — фича инертна, кодекс описывает более позднее поведение (инлайн №3).
4. **[major]** Синк печати односторонний: рекорд получает только `sealed`, но пишет в авторитетный компонент integrity/tier/failures/knowledge — `identify()` молча восстанавливает истлевшую печать (инлайн №4).
5. **[major]** Запечатанный инцидент продолжает стареть и проходить стадии — снятие печати детонирует на высшей стадии (инлайн №5).
6. **[major]** `InfectionSink`: бюджет 64/тик привязан к часам измерения (сбрасывается на мультимире), каденсы и `announcedSecondaryBirths` транзиентны → рестарт-шторм и повторные SECONDARY_BIRTH-кью (инлайн №6).
7. **[major]** `InfectionQueue`: нет `remove(id)` — статическая мапа удерживает рекорды навсегда; отложенные правки живут только в памяти и теряются при рестарте, хотя кодекс обещает обратное (инлайн №7).
8. **[minor]** `spawn()` возвращает несохранённый рекорд при отказе минта — фантом для вызывающих; `OBJECT`-источник при несвязанном спавнере сохраняется без объекта (инлайн №8).
9. **[minor]** Компонент `CURSED_OBJECT_STATE` пишется каждый тик у носимого объекта — сетевой чюрн (инлайн №9).
10. **[minor]** `catchUp` старит все записи по часам оверворлда — междумерное смещение возраста (инлайн №10).

Мелочи без инлайнов:

- `PerceptionOverrideRuntime.tick` зовётся дважды за пульс (свой `%20`-обработчик + вызов из `IncidentRuntime.tick`) — лишний проход players×records каждые 20 тиков.
- `flushPendingDrains` выдаёт `tickZone(..., 64)` каждой записи — загрузка чанка обходит общий бюджет (до N×64 за тик).
- `CursedObjectItem.damageSeal` — параллельная реализация урона печати (без катастрофического броска и `sealFailures`), расходится с `IncidentControl.damageSeal` — на границе предмет↔инцидент нарушается «одна забота — одна система».
- `InfectionPolicy.strippedVariant` возвращает AIR для неучтённых брёвен (bamboo/pale oak) — блоки исчезают без дропа; `spawnTableFor(String,…)` — мёртвый overload (игнорирует templateId).
- `ZoneGeometry.sampleBlocks`: COLUMN-ветка имеет мёртвый тернарник — y-семплинг идентичен сфере; `cullAnimals` использует `AABB.inflate(radius)` — куб вместо формы зоны.
- `IncidentNbt` — набор Capitalized-алиасов «под прозу плана» — мёртвый код.
- `ObjectDwellTracker.noteContainer` без `level` — объект из контейнера без прежней привязки получает `level=null` и не тикает; `accumulatedTicks`-компонент и так выше.
- На LAN-хосте `CursePerception.perceives` через клиентский провайдер моста читает флаг локального игрока при проверке других игроков — краевой десинк фильтра кью.
- `SpawnRequest.radius` / MCP `radius` не ограничены сверху — `scanContainers`/`cullAnimals` на огромном радиусе повесят тик (dev-поверхность, но стоит clamp'нуть).
- `VfxWorldGeometry` расширил package-private API до public для инцидентов — широкий экспорт внутренностей; `SealingTalismanItem` — приватный inner-класс в файле реестра (не по конвенции `Item`-файлов); `ObjectDisplay.nameKeyFor`/`loreLines` — неиспользуемые sugar-overload'ы, `getString()` на сервере хрупок.
- Покрытие: JUnit/GameTest хорошие, но per-tick путь `PressureRuntime` и sealed-эскалация не покрыты — именно там баги; `pressureSpawnsIncident` по сути тестирует `spawn()`, а не давление (частично признано в KNOWN_ISSUES).

## Архитектурные риски на будущее

- **Процесс-широкое mutable-состояние повсюду**: `IncidentControl` (7 статиков), `InfectionSink.CADENCE/budget`, `InfectionQueue.QUEUES`, `ObjectDwellTracker.TRACKED`, `PressureRuntime`, `PerceptionOverrideRuntime` — всё держится на статиках с ручной `clearRuntimeState`-хореографией. `boundStore` по умолчанию — **новый** in-memory `IncidentSavedData`: любое обращение `data()` до `bindStore` молча пишет в выбрасываемое хранилище. Через пару фич это даст перекрёстные утечки состояния — просится агрегированный per-server `IncidentRuntimeState`.
- **Два источника истины для печати**: компонент объявлен авторитетным, но рекорд хранит свои копии полей и пишет их обратно — следующий writer (урон сущностей, баланс печати) наступит на тот же дрейф. Нужен один writer и одно направление синка.
- **Периметр работы = один центр**: весь `tickZone` работает от `record.center`; `secondaries` — данные без механики. Когда узлы получат работу, понадобятся per-center каденсы/бюджеты/очереди — текущие статический `CADENCE` по `record.id` и одна очередь на инцидент не масштабируются без рефакторинга (в main это уже видно — там появились workCenters/pendingEdits; лучше заложить разбиение сейчас, пока потребителей мало).
- **Пакетная циклическая зависимость**: `cursedincident → cursedspirit.perception.CursePerception` (фильтр аудиенса) и `cursedspirit.perception → cursedincident.IncidentPerceptionBridge` (override) — взаимная связь двух пакетов; следующий источник кью потащит целевой пакет снова — фильтр аудиенса стоит поднять в общий vfx/perception-шов.
- **`IncidentControl` растёт в god-object**: 15+ статических операций (spawn/inspect/advance/escalate/seal/unseal/damageSeal/relocate/forceSecondary/identify/cleanup/reseed/pressure…) на одном фасаде; `InspectView` на ~30 полей дублирует рекорд. Под поведенческое обучение и цели фасад не масштабируется — стоит выделять доменные операции (SealService, SpawnService).
- **Клиентский perception-бит глобален**: `ClientPerceptionState.inCriticalZone()` игнорирует аргумент `perceives(entity)` — верно для локального зрителя, но любая будущая проверка «видит ли ДРУГОЙ игрок» будет молча неверной; контракт стоит зафиксировать в доке.
- **Конфигурация зашита в код**: `IncidentTemplates.ALL` и веса — статика; если шаблоны станут data-driven, потребуется отдельный реестр — отметить как принятое решение v1.

## Вердикт

**Request changes** — архитектурный каркас правильный и заслуживает жить дальше, но дефекты выше затрагивают поведение ядра, а не полировку: тикающий баг PressureRuntime делает весь баланс давления декоративным, дрейф печати ломает инвариант «компонент авторитетен», а запечатанная зона продолжает расти по стадиям.

Порядок действий:
1. Починить якорь `PressureRuntime` (`lastTickGameTime = now` на срабатывании периода + отдельный накопитель суток) и заменить `list()` на дешёвый count.
2. Развернуть синк печати в одну сторону (компонент → рекорд полный слепок, либо запрет на запись рекорд→компонент).
3. Заморозить `advanceTo`/эскалацию при `record.sealed` (или зафиксировать обратное в спеке).
4. Сделать каденсы и очередь правок долговечными на `IncidentRecord`; добавить `InfectionQueue.remove(id)` из `onCleanup`/`onRelocated`.
5. Бюджет вести по монотонному `server.getTickCount()`, а не по часам измерения.
6. Дать вторичным узлам реальную per-center работу либо пометить их пассивными в кодексе.
7. `applyTransition`: коммит `record.stage` до `applyStageDelta`.
