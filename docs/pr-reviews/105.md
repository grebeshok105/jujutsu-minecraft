## Сводка

Dev-only слой для in-game верификации: 8 новых `jujutsu_*` тулов в `src/mcpdev`, ring-буфер боевого лога (512 событий), cross-dim resolver сущностей и ops-док `docs/MCP-LANE.md`. В релизную сборку не входит — это подтверждено `auditReleaseJarIsolation` и gate по `-PmcpUpstreamJar`.

**Риск: Medium.** Продакшен-путь не затронут (нет изменений `src/main`/`src/client`), но несколько находок бьют по главному назначению инструментов — доказуемости наблюдений: боевой лог теряет урон смертельного удара, `wait_until` в `any`-режиме молча маскирует сломанные условия, `entity_present` даёт false-positive через измерения.

## Сильные стороны

- Чистая изоляция лейна: отдельный sourceSet, нулевые изменения геймплея, только публичные Fabric/upstream API, без mixin и impl-интерналов — hard rules AGENTS.md соблюдены.
- Верная дисциплина потоков и кодов ошибок: парсинг/валидация входа на HTTP-потоке до `onMainThread`-хопа (коды не сплющиваются в `TOOL_HANDLER_ERROR`), паркинг на `CompletableFuture`, fail-fast при остановке сервера.
- Combat log: синхронизированный snapshot для HTTP-потока, очистка на `SERVER_STOPPED`, атрибуция снарядов по `owner` — продуманные детали.
- По прошлому ревью добавлены pre-validation условий и per-condition отчёт — полезная постмортем-диагностика.
- `docs/MCP-LANE.md` — честный ops-документ: restart-протокол и «капризы» снимут реальную боль у следующих сессий.

## Проблемы

1. **[major]** Летальный удар теряет урон и атрибуцию в боевом логе — `AFTER_DAMAGE` не вызывается, когда урон убил сущность (инлайн `JujutsuCombatLog.java:58`). Самое важное событие для «кто кого убил» пишется с `amount=0`; `damage_type` не записывается вообще.
2. **[major]** `wait_until` в `any`-режиме безусловно глотает `McpException` каждого условия на каждом тике (инлайн `JujutsuWaitUntilTool.java:364`). Комментарий обещает обратное; навсегда сломанное условие неотличимо от «ещё не выполнилось» — молчаливый cap вместо диагностики.
3. **[major]** Два параллельных switch — `validate()` и `evaluate()` — дублируют знание о типах условий (инлайн `JujutsuWaitUntilTool.java:213`). Рассинхрон при добавлении условия станет невидимой ошибкой.
4. **[major]** `entity_present`: `distanceTo(near)` игнорирует измерение → cross-dim false-positive; плюс полный обход `getAllEntities()` всех уровней каждый тик (инлайн `JujutsuWaitUntilTool.java:267`).
5. **[minor]** Drain-курсор `tick <= sinceTick` теряет события, записанные в том же тике после снапшота (инлайн `JujutsuCombatLogTool.java:62`).
6. **[minor]** Таймаут `done.get` привязан к wall-clock, а не к прогрессу тиков — при просадке TPS клиент получает `MAIN_THREAD_TIMEOUT` при живом джобе (инлайн `JujutsuWaitUntilTool.java:121`; отмечено и бот-ревью — остаётся открытым).
7. **[minor]** `entity_type`/`nbt` уходят в dispatcher-команду без валидации; источник — `createCommandSourceStack()` с полными правами (инлайн `JujutsuEntitySummonNearTool.java:95`). Инъекции второй команды через однострочный Brigadier нет, но вход стоит валидировать реестром.
8. **[minor]** `jujutsu_look_at` ставит поворот только на сервере — первый клиентский move-пакет с новым поворотом перезапишет его (инлайн `JujutsuLookAtTool.java:57`). Рецепт «look_at → ability_invoke» живёт только при немедленной связке.
9. **[nit]** `jujutsu_entity_set_health` отвечает `killed:true`/`health:X` на уже мёртвой сущности, ничего не изменив (инлайн `JujutsuEntitySetHealthTool.java:66`).

Мелочи без инлайн-комментариев:

- `docs/MCP-LANE.md` запечатывает машино-специфичный путь `D:/WorkFlow/mcp-spike-scratch/...` — в durable-документе лучше плейсхолдер (AGENTS §14: no temp facts in durable files).
- `docs/MCP_DEV_CONTROLS.md`: таблица tool surface устарела — 8 новых тулов не перечислены.
- `ResourceLocation.parse` в `validate`/`entityPresent` бросает `ResourceLocationException`, а не `McpException` — кривой id уйдёт не под `TOOL_INPUT_INVALID`.
- `radius` у `entity_present` не валидируется: отрицательное значение молча никогда не совпадёт.
- `limit` у `jujutsu_combat_log`: границы 1–512 объявлены в схеме, но `optInt` их не enforce-ит — `limit=0` молча отдаёт всё.
- `.agent-runs/mcpdev-tools/INDEX.md` закоммичен и удалён в том же PR — шум в истории (файл под gitignore, значит сначала ушёл в индекс принудительно).

## Архитектурные риски на будущее

- **Дублирование async-wait каркаса.** `JujutsuWaitUntilTool` копирует из `JujutsuTicksWaitTool` ~100 строк механики: константы `TICK_MS`/`TIMEOUT_MARGIN_MS`, `WaitJob` с self-rescheduling `TickTask`, тройной catch у `done.get`, volatile-результаты. Это уже второй ждатель — третий (ожидание фикстур, инцидентов) неизбежен. Общий helper уровня `TickPoll.await(server, capTicks, Predicate<MinecraftServer>) → CompletableFuture<...>` уберёт конкурентный код из тулов и не даст копиям разойтись (уже разошлись: здесь нет `elapsedMs`, там нет per-condition отчёта).
- **Пересечение поверхности тулов.** `jujutsu_ticks_wait` с `player_uuid` — частный случай `wait_until` с `cooldown_clear` (PRIMARY). Две реализации cooldown-ожидания будут дрейфовать; стоит сузить `ticks_wait` до чистого тик-слипа и зафиксировать границу в MCP-LANE.md.
- **Точка расширения условий.** Сейчас условие = две правки в двух switch + строки javadoc. По мере роста смоук-сценариев условий станет больше — односайтовый реестр (имя → валидатор + эвалуатор) окупится уже на следующем условии.
- **Singleton-state в рантайме компаньона.** `JujutsuCombatLog.BUFFER` статичен и чистится по `SERVER_STOPPED` — корректно для одного мира. При появлении второго stateful-регистратора (лог инцидентов, трейс ability) попросится централизованный `clearAll`-хук — ввести его дёшево уже сейчас.
- **Box-diff resolution UUID.** Приём «diff сущностей в боксе до/после» — вынужденный костыль вокруг upstream `/summon` (issue заведён). Паттерн хрупок (пассажиры, спавн вне бокса → `resolved:false`) — при повторном использовании стоит вынести в общий resolver со ссылкой на upstream-issue.
